3.4 Greenfield New System Design (summary, core pieces)

Capability boundaries & decomposition
- API Layer (HTTP) — request validation, idempotency key enforcement
- Scheduler/State service — durable store for appointment state + transactional outbox
- Adapters — to calendar providers, each with circuit-breaker and rate-limits
- Outbox Dispatcher — reliable side-effect runner with retries/backoff
- Reconciler/Audit — periodic reconciliation of provider vs. local state

State Machine (appointment)
- States: created -> requested -> confirmed -> finalized | cancelled | failed
- Key transitions guarded by idempotency + optimistic concurrency (versioning)
- Compensation events: on provider later-notify (conflict) -> cancelled + audit + notification

Resilience strategies
- Idempotency key persisted for TTL (store results; return cached response for key hits)
- Provider calls: retry with exponential backoff (e.g., 100ms * 2^n), capped, attempts=5
- Circuit-breaker per provider (open after N failures, short-circuit requests)
- Transactional outbox: write state + outbox message in one DB txn; dispatcher reads outbox to call provider
- Reconciler runs to detect inconsistent states and triggers compensation or manual ops

Simple ASCII architecture
Client -> API -> AppointmentService (state + outbox DB)
                      |-> Outbox Dispatcher -> Calendar Adapter -> Provider
                      |-> Reconciler -> Audit DB / Tooling

Key interface sample JSON (CreateAppointmentRequest)
{
  "idempotency_key": "uuid-or-client-key (<=36 chars)",  // required
  "user_id": "string",  // required
  "start_ts": "ISO8601 string",  // required
  "duration_minutes": 1..1440,  // required
  "metadata": { ... }  // optional, size <= 2KB
}

Validation constraints
- start_ts should be in allowed scheduling window, duration 1..1440, idempotency_key present and capped.

Migration & parallel run (practical steps)
- Shadow reads and read-only checks vs. new service
- Dual-write: only if idempotency and outbox ensure side-effects are deduplicated; prefer queueing shadow writes and auditing
- Backfill: export legacy data -> upsert into new DB -> run reconcilers to close gap
- Cutover: 5%->25%->50%->100% ramp with rollback plan to pause new-service writes and replay outbox to legacy
