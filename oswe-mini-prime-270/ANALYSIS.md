# Legacy System Analysis & Greenfield Replacement Plan

This document captures the analysis of the legacy routing code (issue_project) and the design rationale for a greenfield replacement (scheduler). It collects assumptions and a checklist, summarizes background context, provides current-state issues and root-cause analysis, and recommends a new design and testing plan.

**2. Background and Legacy Context**
- Legacy module: `dijkstra_shortest_path` was used to compute routes but lacked negative weight detection and incorrectly marked nodes visited prematurely (pre-finalization).
- Root function: routing in logistics, but these mechanics don't map 1:1 for appointments — mapping to scheduling (booking) for demonstration.
- Core flows: create appointment (idempotent), contact calendar to book and return result.
- Dependencies: external calendar API. Legacy code had shallow tests focusing on algorithmic correctness but lacking runtime resilience patterns.

**3. Current-State Scan & Root Cause Analysis**
Table: Category | Symptom | Likely Root Cause | Evidence / Needed Evidence

- Functionality | Wrong routing results in presence of negative weights | Dijkstra used without negative-weight validation; early node finalization; test shows expected path not found | See [src/logistics/routing.py](issue_project/src/logistics/routing.py) and tests/test_routing_negative_weight.py

- Reliability | Post-appointment side effect (calendar) fails without replay | No outbox or durable retry; direct synchronous call to calendar; no retry/backoff strategy variant | Observed in legacy architecture: no outbox pattern

- Maintainability | Single-file algorithm, tight coupling, limited tests and simulation | Legacy modules are minimal and not separated for failure semantics; code comments indicate intentional bugs | file inspection shows naive dijkstra and test failing to match expectations

- Security | Not relevant in the legacy demo dataset; but in real deployment, IDs, access tokens, and user fields must be masked | No production security design found; assume need for transport TLS and tokens

- Performance | None measured; algorithmic complexity is O(E log V) for Dijkstra but incorrect operations might miscompute routes | Need performance metrics and benchmarks

- Cost | Unknown, but routing algorithms in compute nodes are cheap; external calendar calls may be rate-limited and cause retries | Data missing: cost per external call and rate limits

High-priority issues: reliability due to synchronous side-effects involving calendar. Proposed hypothesis chain and validation:
- Hypothesis: A single synchronous calendar call fails → request fails or is inconsistent. Validate by simulating calendar failure; expect appointment created but downstream not booked → outbox must be introduced.
- Fix: Implement transactional outbox + background replay. Causal chain: database write -> outbox event enqueued -> background worker tries to notify calendar -> on success mark the outbox processed. On failure, keep event for retry.

**4. Greenfield Design (Target State)**
Goals: Resilient scheduler microservice with the following properties:
- Idempotent create: allow safe retries using `request_id` header or dedupe token.
- Outbox for side effects: guarantee at-least-once delivery with background replay.
- Retry/backoff and timeout: avoid blocking for long time and gracefully degrade.
- Circuit-breaker simulation: avoid calling downstream repeatedly during outage.
- Audit and reconciliation: ability to list and replay outbox events; metrics on success/failure and retry counts.

Service decomposition:
- API Gateway / Ingress -> Scheduler Service -> Storage (DB) & Outbox -> Calendar Provider.
- Optional: Notification service to inform user once calendar booking completes.

State machine (appointment lifecycle):
- INIT -> CREATED (DB write and outbox) -> BOOKING_IN_PROGRESS -> BOOKED or FAILED (compensation may be required)

Idempotency & schema:
- `request_id`: string (UUID), required in `POST /appointments` header or body.
- `appointment_id`: UUID assigned in the DB.
- `user_id`: masked when logged.
- `status`: Enum: created, in_progress, booked, failed.

JSON schemas (small):
- AppointmentRequest: { request_id: string, user_id: string, start_time: datetime, end_time: datetime, location: string, details?: string }
- Appointment: { appointment_id, request_id, user_id, start_time, end_time, location, status }

Migration/Parallel Run:
- Start with a shadow/dual-write mode where both legacy and new systems receive traffic and produce events for comparison.
- Use dual-write + reconciliation (compare pre/post DB states) for the initial weeks.
- Cutover: Move ingress to new service and watch outbox growth. If outbox meets SLA (no persistent backlog), stop legacy service.
- Rollback path: revert ingress router to legacy and keep a snapshot of new DB.

**5. Testing & Acceptance Plan**
- Derived Integration Tests (extracted from crash points and risk):
  - Idempotency test: same request repeated returns same appointment id and does not cause duplicates.
  - Retry/backoff: Fluent retry on transient failures, ensure eventual success with controlled backoff.
  - Timeout propagation/circuit-breaker: When calendar times out, system returns OK with outbox persisted and not blocking client; monitor outbox growth.
  - Compensation / Saga (Outbox): On failure, manual/tran replay marks booking as completed and outbox processed.
  - Happy Path: Calendar responds quickly; outbox is processed and appointment state is `booked`.

Test structure (automatable):
- Preconditions: clear store.
- Steps: execute sequence of API calls with monkeypatched calendar behaviors.
- Expected: assert API responses and store/outbox states.
- Observability: structured logs include `request_id` and events for `outbox_enqueued`, `outbox_processed`, `calendar_call_start`, `calendar_call_fail`.

Acceptance Criteria (Example SLO / SLA)
- Given: Network glitches and downstream failures up to 3 transient errors
- When: Client makes appointment creation call
- Then: Service responds in < 500ms with 201, and outbox is enqueued; calendar is booked within 60s or outbox replay results in booked state
- p50 latency < 200ms, p95 < 500ms, error rate < 1% under test load

**6. Observability, Logging, and Security**
- Use JSON structured logs with fields: timestamp, level, service, request_id (uuid), user_id (masked), component, message.
- Trace context: include tracing headers (X-Trace-Id)
- Mask user details in logs (for privacy).

**7. Migration Plan**
- Add a shadow route to capture events from production traffic and publish a reconciliation report.
- Log differences and build a `compare_report.md` focusing on booking success rate and outbox growth.

**8. Next Steps**
- Replace InMemoryStore with durable DB (Postgres) and transactional outbox table.
- Add a background worker or use message broker (Kafka/RabbitMQ) for outbox processing.
- Add instrumentation (Prometheus) and dashboards for outbox growth, retries, booking fail rates.
